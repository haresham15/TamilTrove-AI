# TamilTrove V2 Implementation Plan

## 1. Vision

TamilTrove V2 will evolve from a semantic movie-search demo into a measurable, multilingual, personalized Tamil-cinema discovery platform.

The product should help users:

- Describe a story, mood, theme, or viewing situation in English, Tamil, or Tanglish.
- Discover relevant Tamil films instead of receiving only popularity-based recommendations.
- Understand why each movie matched their request.
- Save, rate, dismiss, and organize movies.
- Receive recommendations that improve through continued use.
- Trust the movie metadata and recommendation explanations.

The engineering goal is to demonstrate a production-quality recommendation system with data pipelines, information retrieval, personalization, evaluation, observability, automated testing, and deployment.

## 2. V2 Success Criteria

V2 is complete when the following conditions are met:

- Search works in English, Tamil, and common Tanglish phrasing.
- The relevance benchmark contains at least 100 reviewed query-to-movie judgments.
- The system achieves at least 80% Hit@5 on the reviewed benchmark.
- No release can reduce NDCG@10 or MRR beyond an agreed regression threshold.
- Users can register, sign in, rate movies, maintain a watchlist, and dismiss recommendations.
- Personalized recommendations respond to stored user preferences.
- Every recommendation includes an evidence-based explanation.
- Movie ingestion and enrichment are repeatable, validated, and versioned.
- Backend p95 search latency is measured and remains below the agreed production target.
- Critical frontend and backend workflows are covered by automated tests.
- CI validates formatting, linting, types, unit tests, integration tests, relevance metrics, and builds.
- The production deployment exposes health, readiness, metrics, and structured logs.

## 3. Scope

### 3.1 Must-have features

- Validated movie catalog stored in PostgreSQL.
- Hybrid semantic and lexical search.
- English, Tamil, and Tanglish queries.
- Structured filters and sorting.
- User authentication and profiles.
- Watchlists, ratings, likes, and dismissals.
- Personalized recommendations.
- Evidence-based match explanations.
- Offline relevance-evaluation suite.
- Automated data ingestion and quality checks.
- Unit, integration, and end-to-end tests.
- CI/CD and production observability.

### 3.2 Should-have features

- Shareable movie collections.
- Similar-movie pages.
- Search and recommendation history.
- Recommendation feedback controls.
- Admin data-quality dashboard.
- Model and ranking experiment tracking.
- Feature flags for ranking experiments.

### 3.3 Deferred features

- Native mobile applications.
- Social messaging or a full social network.
- Video streaming or copyrighted media hosting.
- Generic chatbot functionality without grounded retrieval value.
- Paid subscriptions.
- Large-scale collaborative filtering before sufficient user activity exists.

### 5.2 Data rules

- Titles are not unique without release year and language.
- External identifiers must be stored separately from internal IDs.
- All enriched fields record their source and last update time.
- User-generated and externally sourced content remain distinguishable.
- Embeddings are regenerated only when their input content hash or model version changes.
- Personally identifying data is never written to analytics logs.

## 6. Data Ingestion and Quality Pipeline

### 6.1 Pipeline stages

1. Load source records into a staging table.
2. Normalize whitespace, names, dates, genres, and missing values.
3. Match identities using title, year, director, cast, and external identifiers.
4. Detect duplicates and conflicting records.
5. Enrich only records with a sufficiently confident identity match.
6. Validate enriched summaries against the matched movie identity.
7. Quarantine suspicious or incomplete records.
8. Promote validated records into canonical tables.
9. Generate embeddings for changed content.
10. Produce a versioned data-quality report.

### 6.2 Validation checks

- Required-field completeness.
- Valid release-year and runtime ranges.
- Allowed poster protocols and hosts.
- Summary-to-movie identity consistency.
- Duplicate title/year/language combinations.
- Director and cast consistency between sources.
- Empty, unusually short, or biography-like overviews.
- Poster images that depict a person or unrelated film instead of the movie poster.
- Non-finite embeddings and incorrect vector dimensions.
- Exact alignment between canonical movie rows and embeddings.

### 6.3 Provenance

Each imported field should record:

- Source system.
- Source identifier or URL.
- Retrieval timestamp.
- Transformation version.
- Confidence where applicable.

### 6.4 Operational behavior

- Make ingestion idempotent.
- Retry temporary failures with bounded exponential backoff.
- Respect source rate limits and terms of use.
- Never overwrite valid canonical data with a lower-confidence match.
- Generate a dry-run report before applying large changes.
- Retain the previous dataset version for rollback.

## 7. Search and Ranking

### 7.1 Retrieval stages

1. Normalize the query.
2. Detect query language and probable intent.
3. Parse explicit filters such as year, genre, actor, director, and popularity.
4. Generate a multilingual semantic embedding.
5. Retrieve semantic candidates from pgvector.
6. Retrieve lexical candidates from PostgreSQL full-text search.
7. Fuse candidate lists.
8. Apply structured filters.
9. Rerank using relevance, preference, quality, and diversity features.
10. Generate evidence-based explanations.

### 7.2 Ranking features

- Semantic similarity.
- Lexical title, genre, theme, and overview similarity.
- Exact actor and director matches.
- Release-year compatibility.
- User preference similarity.
- Previously liked and disliked themes.
- Movie-data quality score.
- Popularity or hidden-gem preference.
- Result-set diversity.
- Previously dismissed or consumed items.

### 7.3 Rank fusion

Begin with a transparent weighted ranker or reciprocal-rank fusion. Every weight must be configuration-driven and included in a ranking-version identifier.

Later, once interaction data is sufficient, evaluate a learning-to-rank model. Do not train on raw clicks without accounting for position bias.

### 7.4 Filters

- Release-year range.
- Genre and theme.
- Actor and director.
- Runtime.
- Certification.
- Popularity or hidden-gem range.
- Minimum data-quality confidence.
- Exclude watched or dismissed films.

### 7.5 Query behavior

- Preserve an empty-query discovery mode rather than treating it as an error.
- Return actionable validation messages.
- Cancel stale client requests.
- Cache only safe, non-personalized query results.
- Return the ranking version and component scores in development mode.

## 8. Tamil and Tanglish Retrieval

### 8.1 Supported query forms

- English: `A political courtroom drama about injustice`.
- Tamil: `அநீதியை எதிர்த்து போராடும் நீதிமன்ற படம்`.
- Tanglish: `Kaithi maari one night action thriller`.
- Mixed language: `Village setting-la emotional family drama`.

### 8.2 Implementation

- Select a multilingual sentence-embedding model after benchmarking candidates.
- Preserve Tamil script during normalization.
- Add conservative Tanglish normalization for common words and spelling variants.
- Maintain a domain vocabulary for Tamil cinema terms, genres, names, and colloquialisms.
- Avoid translating proper names unless an alias is explicitly known.
- Store normalized query forms for debugging while retaining the original query.

### 8.3 Evaluation slices

- English plot descriptions.
- Tamil plot descriptions.
- Tanglish plot descriptions.
- Actor/director lookup.
- Mood and theme queries.
- Hidden-gem discovery.
- Queries with structured constraints.
- Short, vague, and misspelled queries.

No model should be adopted based on English-only aggregate accuracy.

## 9. Personalization

### 9.1 Initial preference profile

During onboarding, allow users to select:

- Movies they enjoyed.
- Favorite genres and themes.
- Preferred eras.
- Mainstream versus hidden-gem preference.
- Preferred languages or dubbing tolerance.

### 9.2 Content-based profile

- Build a weighted user vector from liked, highly rated, and saved movies.
- Apply negative weights for dislikes and dismissals.
- Decay weak or old signals where appropriate.
- Keep explicit ratings stronger than passive clicks.
- Allow users to reset or edit preference history.

### 9.3 Recommendation surfaces

- `For You` personalized feed.
- `Because you liked...` rows.
- Similar movies.
- Continue exploring a theme.
- Hidden gems for the user.
- Recently added movies matching known preferences.

### 9.4 Cold start

- Use onboarding selections.
- Offer curated collections.
- Fall back to diverse, high-quality catalog results.
- Never present a popularity-only feed as personalized.

### 9.5 Future collaborative signals

Add collaborative filtering only after sufficient interaction volume exists. Use time-based train/test splits and compare it against the content-based baseline.

## 10. Recommendation Explanations

Every explanation must be grounded in ranking evidence.

Examples:

- `Strong match for one-night thriller, prisoner, and chase themes.`
- `Recommended because you liked Kaithi and Vikram.`
- `Lower mainstream-popularity score matches your Hidden Gem setting.`

### 10.1 Explanation inputs

- Matched query phrases.
- Shared genres and themes.
- Similar liked movies.
- Structured filter matches.
- Semantic and lexical score contributions.
- Hidden-gem contribution.

### 10.2 Guardrails

- Never claim a plot element absent from trusted metadata.
- Clearly distinguish factual metadata from generated summaries.
- Do not expose raw user-history details in public or shared pages.
- Provide a fallback explanation when confidence is low.

## 12. Evaluation Program

### 12.1 Benchmark dataset

Create a version-controlled benchmark with at least 100 queries. Each record should contain:

- Query.
- Language and query category.
- Relevant movies with graded relevance judgments.
- Reviewer notes.
- Dataset version.

Use multiple reviewers for ambiguous cases and record disagreement instead of forcing false certainty.

### 12.2 Metrics

- Hit@1, Hit@5, and Hit@10.
- Precision@K and Recall@K.
- Mean Reciprocal Rank.
- NDCG@K for graded relevance.
- Catalog coverage.
- Result diversity.
- Zero-result rate.
- p50, p95, and p99 latency.
- Error rate.

### 12.3 Experiment tracking

Every ranking experiment records:

- Code commit.
- Dataset version.
- Embedding model and version.
- Ranking weights.
- Benchmark metrics and per-slice results.
- Runtime and memory measurements.

### 12.4 Release gate

A change cannot ship if:

- It causes an unexplained relevance regression.
- A language slice falls below its threshold.
- It breaks result diversity or catalog coverage limits.
- Latency or memory exceeds the deployment budget.
- Data-quality validation fails.

### 13.2 API requirements

- Stable identifiers instead of array indexes.
- Explicit pagination.
- Consistent error envelope.
- Request IDs and ranking-version metadata.
- Authentication and ownership checks.
- Rate limiting for expensive or abusive traffic.
- OpenAPI examples for successful and failed requests.

## 14. Security and Privacy

- Keep secrets server-side.
- Use a managed authentication provider or a well-reviewed authentication library.
- Validate authorization for every user-owned resource.
- Use secure, HTTP-only cookies where applicable.
- Apply CSRF protection according to the chosen authentication approach.
- Restrict CORS to known origins.
- Validate and normalize all external URLs.
- Add request-size and rate limits.
- Avoid logging authentication tokens, raw credentials, or sensitive profile data.
- Provide account export and deletion flows.
- Document analytics and recommendation-data usage.

## 21. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Incorrect source matching | Wrong summaries, posters, and embeddings | Strong identity matching, provenance, quarantine, and review tools |
| Small evaluation set | Misleading accuracy claims | Expand and stratify judgments; separate development and test sets |
| Popularity bias | Repetitive mainstream results | Measure coverage and diversity; expose user-controlled popularity preference |
| Cold-start personalization | Weak new-user experience | Explicit onboarding and curated fallback collections |
| Sparse interaction data | Collaborative models underperform | Keep content-based ranking as the baseline |
| Multilingual quality imbalance | Tamil/Tanglish users receive worse results | Maintain separate language metrics and release thresholds |
| Model cold starts | Slow first request | Preload at build/startup, add readiness checks, and measure startup time |
| Unbounded infrastructure scope | Delayed product delivery | Require measured justification for Redis, queues, and additional services |
| Explanation hallucination | Loss of user trust | Generate explanations from deterministic ranking evidence |
| Position-biased clicks | Misleading learning signals | Randomized experiments where safe and bias-aware offline evaluation |

## 23. Definition of Done

A V2 task is done only when:

- Acceptance criteria are met.
- Relevant tests are added and passing.
- API and user-facing behavior are documented.
- Error, loading, empty, and permission states are handled.
- Accessibility is considered.
- Metrics and logs are sufficient to diagnose failures.
- Database or data changes include migration and rollback instructions.
- Search changes include evaluation results.
- Security and privacy implications are reviewed.
- No secrets, local environments, generated caches, or private data are committed.

## 24. Recommended Starting Sprint

The first implementation sprint should remain narrow:

1. Pin the backend runtime and document clean local setup.
2. Move ranking functions out of `main.py` into testable modules.
3. Add `/health` and `/ready` endpoints.
4. Commit a 25-query starter benchmark with English, Tamil, and Tanglish categories.
5. Add a benchmark runner that outputs Hit@K, MRR, NDCG@10, and latency.
6. Add backend unit tests and a GitHub Actions workflow.
7. Record the V1 baseline before introducing PostgreSQL or a new embedding model.

This creates the measurement and reliability foundation required to make every later V2 improvement credible.
